用户的想法很简单，也很疯狂：

"我要做一个工具，让任意 Linux 发行版都能安装任意 Linux 发行版的离线软件包。"

换句话说：在 Ubuntu 上装 RPM，在 Arch 上装 DEB，在任何系统上装任何格式的包。
不联网，不依赖原生包管理器，纯解压安装。

这不是一个新的包管理器。这是一个"万能适配器"。

Kimi 的开发过程（从对话中可以看到的演进）：

v0.1: "uni-pkg" — 单文件脚本
  - 最初的雏形，一个 bash 脚本
  - 支持 deb/rpm/pacman/appimage/tar
  - 用系统自带的 dpkg/rpm/pacman 来安装（依赖原生工具）

v0.2: 纯脚本版 — 去掉所有依赖
  - 用户说"这个包管理器的安装方式改成用脚本的吧，我的linux发行版
    要可以安装所有发行版的安装包"
  - Kimi 重写了纯脚本版，完全不依赖 dpkg/rpm/pacman
  - 纯手动解压安装

v0.3: 自植入 upkg — 运行一次就变系统命令
  - 用户说"这个脚本要运行一次后直接植入进系统内核，
    然后下次操作就可以直接用他的专属命令来运行"
  - Kimi 加入了 self_install 机制
  - 命令名改为 upkg
  - 运行一次后自动植入系统

这个过程中用户反复强调的要点：
- 必须是纯 Shell
- 必须真正能用
- 必须支持所有发行版
- 必须离线工作
- 必须模块化
- 命令要简单

发现的 Bug（共 5 个）：

  Bug 1 (🔴 高): RPM XZ payload 不支持
    文件: modules/pkg-handler.mod → _extract_rpm_pure()
    现象: 现代 RPM 包（如 QQ）的 cpio payload 用 XZ 压缩
          代码只处理 gzip，导致解压失败
    修复: 新增 XZ/gzip/bzip2/zstd 四种压缩格式检测
          magic bytes 判断 → 对应解压工具
          回退到 Python 标准库（lzma/gzip/bz2）

  Bug 2 (🟡 中): pacman .PKGINFO 的 pkgver 解析失败
    文件: modules/pkg-handler.mod → get_pkg_version() + get_pkg_name()
    现象: .PKGINFO 格式 "pkgver = 1.0-1"（等号两边有空格）
          grep "^pkgver" | awk -F'= ' 匹配不上
    修复: 改用 grep -E "^pkgver\s*=" | sed 's/^pkgver\s*=\s*//'
          同时修复了 pkgname 的同样问题

  Bug 3 (🟢 低): manifest.json.tmp 残留在 .kurali 包中
    文件: modules/pkg-handler.mod → pack_kurali()
    现象: 文件数和大小写入 manifest.json.tmp，但没有合并到
          manifest.json，也没删除，被打包进 .kurali
    修复: 改为直接用 sed 修改 manifest.json 内容

  Bug 4 (🟢 低): AppImage symlink 用 "AppRun" 而非包名
    文件: kuraliAll.sh → cmd_install() 符号链接部分
    现象: find_executables 返回 AppRun 路径，
          basename 是 "AppRun"，symlink 就叫 AppRun
    修复: 当 bn=="AppRun" 且 format=="appimage" 时，
          用 pkg_name 作为 symlink 名

  Bug 5 (🟢 低): _load_distro 独立 source 时 has_cmd 未定义
    文件: modules/system.mod → _load_distro()
    现象: has_cmd 定义在 core.mod，如果单独 source system.mod
          会报 "has_cmd: command not found"
    修复: 用 declare -F 检查 has_cmd 是否存在，
          不存在时回退到 command -v
